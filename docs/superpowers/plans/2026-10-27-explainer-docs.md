# How it works: the explainer documentation section — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a fifth documentation section, `docs/explained/`, that explains in plain words how the parts of a semiconductor device work (silicon and carriers, bands, the pn junction, the transistor's parts, the MOS capacitor, the MOSFET), grounded in this repo's committed artefacts: every number on a page comes from a committed file by substitution, or is a textbook value labelled and cited as such, or is an idealised example labelled as such and computed by the docs build from stated inputs. Every figure is generated at docs build time from committed files by one figure module, in a light and a dark twin. The pages embed the 3D renders of the renders plan as they land, with a generated plain diagram until then. Each task ends in a reviewed, merged PR that leaves `main` standing on its own.

**Owner's words** (spec §16, 2026-10-27): "Add to the spec that there should be a section of the documentation which is designed to be a general explaination how the various parts of semiconductors work using the references / assets from the repo to ground things in the real world."

**Architecture:** One new host-side package, `src/gf180tcad/explain/`, imported only by `docs/conf.py`, `gf180tcad.docgen` and the tests, never by a generator module. (1) `explain/numbers.py`: a registry of named numbers, each read from a committed file (JSON key path, TOML key, CSV column with a row selector, the `metrics.json` of a device and geometry) or from `data/explain/textbook.toml` (textbook values, each with its citation), optionally passed through one formula: a shared one from `gf180tcad.derive` (the renders' formula module, for example the Boltzmann densities), or an idealised-example formula from the closed table `explain/idealised.py` (mass action, Boltzmann Fermi level, built-in potential, depletion width, oxide capacitance, flat-band and threshold voltage of the idealised stack), and formatted with a stated number of significant digits and a unit. `substitutions()` returns `{"x_<name>": "<value> <unit>"}`, which `docs/conf.py` merges into `myst_substitutions` at configuration time, so a page writes `{{ x_n_ch_nfet_cal }}` and the build prints the committed value. (2) `explain/figures.py`: every explainer figure, drawn with the existing deterministic SVG settings of `gf180tcad.plots` (fixed hash salt, text as text, no date), sized for a phone, and written twice (light and dark palette) into `docs/_generated/explained/` by `docgen.generate()` at `builder-inited`, like the results pages. Data readers are shared with docgen (the 1D and SPICE curve readers move from private `docgen` helpers into `explain/data.py` or stay in docgen as public functions; nothing is copied). (3) `explain/model.py`: one source model of the device drawn on every page (the 1D stack and the 2D cell: poly, oxide, body, source and drain, junction depth, with their dimensions and doping), re-drawn per page with that page's part highlighted and the rest muted, and an exaggeration statement generated from its scale factors. The model is built **only from committed files and docs-group imports**: `cv.meta.json` (`l_um`, `geometry.w_um`, `meshed_t_ox_nm`, `contacts`), the process file (`param.xj_um`, `param.sd_peak_cm3`, `param.ngate_cm3`), the 1D meta's `stack` and the constants `gf180tcad.tcad.moscap1d.POLY_UM` and `BODY_UM` (`moscap1d`, `analytic`, `mesh`, `calibration` and `process` import only the standard library and `gf180tcad` at top level). It never calls `gf180tcad.tcad.stack.cell`, which needs `gf180mcu.cells`, `shapely`, `gplugins.devsim.doping` and `gdsfactory` (`stack.py` lines 174–363), none of which is in the `docs` dependency group (`pyproject.toml` lines 27–33) that Read the Docs (`.readthedocs.yaml`, `--only-group docs`) and CI (`ci.yml` line 58) install. The lateral extent of the drawn source and drain is a `STYLE` quantity, named in the generated exaggeration statement ("source and drain width drawn, not to scale"), until the renders plan's Task R0 commits a reduced mesh window for the job, whose region outlines the model then reads instead. Nothing generated is committed; the docs build stays offline and deterministic.

## Global Constraints

All Phase 2 Global Constraints apply where they touch the docs (licences, git rules, public data, documentation links, host budget). In addition:

- **Every number from a committed file, mechanically.** A number on an explainer page enters by `{{ x_<name> }}` substitution from `gf180tcad.explain.numbers`. The registry entry names its kind: `committed` (a file under `data/` or `results/`, read by key), `textbook` (`data/explain/textbook.toml`, one entry per value with `source` naming a `literature.md` anchor and the chapter, section or table, and `unit`), or `idealised` (a formula from `explain/idealised.py` over named inputs, each itself a registry entry). The page sentence says which kind it is: "this repo's calibrated nfet body doping", "the textbook value ([Sze and Ng](…), ch. 1)", "an idealised abrupt junction with this repo's doping". A hand-typed number is allowed only where substitution cannot reach (a figure caption written by the figure module counts as substituted) and is then listed in `tests/test_doc_numbers.py` `CASES` with its source. `tests/test_explained.py::test_no_bare_numbers` fails on any digit on an explainer page outside: math, code spans, roles and their targets, substitutions, link targets and link text of citations (`[Sze and Ng](…)`, "ch. 4", "§10.2"), issue and PR numbers (`#46`), and a fixed list of proper names held in the test (`GF180MCU`, "5 V transistor" as the device's name, `nfet_05v0`, `pfet_05v0`, `SiO₂`, "1D", "2D", "3D", "Tier 1" to "Tier 3", "BSIM4", the geometry ids). The per-line `<!-- number-ok: reason -->` opt-out exists for the rare remaining case and the reviewer reads every one. `::test_non_committed_values_are_labelled`: a sentence carrying a substitution of kind `textbook` contains a link to a `literature.md` anchor (`lit-*`), and one of kind `idealised` contains the word "idealised"; `substitutions()` also offers `x_<name>_label` ("textbook value", "idealised example") for pages that want the label written by the registry.
- **Every figure from a committed file, mechanically.** No figure is hand-drawn, and no number is typed into `explain/figures.py` or `explain/model.py` except styling (sizes, colours, line widths, label offsets) kept in one `STYLE` table at the top of `explain/figures.py`, and the 0, 1, 2, −1 of indexing. `tests/test_explained.py::test_figure_code_has_no_numeric_literals` (an AST scan, as the renders plan's `test_scene_builders_have_no_numeric_literals`) enforces it. A figure's data come from registry entries or from the shared data readers, so a figure and the sentence beside it can never disagree.
- **One source model, many views.** The device diagram on every page is `explain.model.device(device, params, geometry)` drawn by `figures.cross_section(model, highlight=<part>)` or `figures.stack_1d(model, highlight=<part>)`. A page about one part highlights that part and mutes the rest (docs-writing, pictures rule 3); a crop carries the whole cell as an inset (rule 4). A fix to the model fixes every page.
- **Exaggeration is data.** A diagram not to scale carries its scale factors in `explain.model`, and the statement ("oxide thickness ×40, not to scale") is generated from them into the figure and its caption, as spec §10.1 requires of the renders. One factor per drawn quantity, the same for both devices and every geometry (spec §10.1 camera conventions): read from `render/style.toml` `[scales]` once the renders plan's Task R2b commits it, and until then from `STYLE`, which E4 then reduces to a read of `[scales]`. Never a factor computed per device.
- **Light and dark are one figure.** Each figure is written as `<name>-light.svg` and `<name>-dark.svg` from one palette table (Okabe–Ito categories, cividis for magnitudes, a diverging map for signed quantities, the renders' material colours once `render/style.toml` exists), and embedded with the `{image}` directive twice, classes `only-light` and `only-dark` (Furo shows the one that matches the reader's theme). The reader never chooses between links.
- **Phone first.** Explainer figures are 6.4 × 4.8 in with 12 pt text. `gf180tcad.plots.figure_svg` is fixed at 10 × 4 in today (`plots.py` lines 37 and 94), so E0 adds a `size` parameter whose default keeps every existing generated SVG byte-identical. An SVG is scaled to the content width, so at 400 px the text is 12 pt × 400 / (6.4 × 72 pt) ≈ 10.4 px high, independent of dpi; `tests/test_explained.py::test_figures_legible_at_400px` computes that from `STYLE` and requires at least 9 px. Tables follow spec §10.3 (one value per cell, at most 5 columns of numbers or 3 with prose) and are checked at 400 px by screenshot.
- **One page type per page.** Every page in `docs/explained/` is an explanation (noun title, the one question in the opening sentences, at most seven headings, no numbered steps, a diagram where it replaces the longest paragraph, and each concept in plain words first, then its equation as `$$` display math with the literature reference, as spec §10.2 requires), except `docs/explained/index.md`, a landing page (one line per page). A page that starts to instruct links a how-to in `docs/reproduce/` instead.
- **Present state, no hedges, no future.** Spec §10.3: no hedge word, no "not yet", no history phrase, no promise. A missing render is not mentioned; the page shows the plain diagram. A missing TCAD MOSFET result is stated as the present state in one sentence linking the roadmap, never as "coming".
- **Honest about the gap** (spec §10.2). Each page ends with a section "Where this repo's results differ" that links the results and limitations pages of the same device and states, with its evidence, where the simple picture and the simulated or SPICE result differ.
- **No provenance change.** `gf180tcad.explain` is imported by no module in any hashed closure (`tests/test_explained.py::test_explain_in_no_generator_closure`: the TCAD entry points, `gf180tcad.reference.GENERATOR_MODULES` and the render closure); no committed tree is restamped; `tests/tcad/test_tcad_provenance.py::test_committed_tcad_provenance_current` and `tests/test_results_provenance.py` stay green. A reader moved out of `gf180tcad.docgen` goes to `gf180tcad.explain.data`, never into a hashed module (`gf180tcad.io`, `gf180tcad.metrics`, `gf180tcad.devices` or any other name in those closures), because moving code into a hashed module changes its hash and restamps its trees. `gf180tcad.quantity` is in the render closure only (Decisions); no SPICE or TCAD closure imports it.
- **Logs.** Every long command writes complete stdout and stderr to a file under the worktree's `tmp/`, with `set -o pipefail`; implementers report exit codes and log paths. Pytest runs as `uv run --locked pytest -rs -v -m "not sandbox" …`. Pushes run in the background or with a timeout of at least 300 s (the pre-push hook runs tests), never with `--no-verify`.

## Decisions

**Decision: figures and numbers are built, not committed.** The explainer's figures and substituted numbers are computed at docs build time from committed files, as the generated results pages are (spec §10: "Results pages are generated from the hashed result files"). A committed SVG or number table would need a staleness test and a regeneration rule; a built one cannot be stale. `test_svg_deterministic` is extended to the explainer figures (two fresh processes, identical bytes), so a build is reproducible. Renders are the exception, because they cannot be made at build time (Blender, hours): they are committed by the renders plan with their manifests and only embedded here.

**Decision: how the explainer is registered, and why no generator section is needed.** The renders plan adds a top-level `renders` section to `generators.json` (renders plan, Task R2b) because renders are committed artefacts with a `provenance.json`, read only by `gf180tcad.render.provenance` and never by `gf180tcad.tcad.generator_files()`. The explainer commits no generated artefact, so it has no tree, no `provenance.json` and no `generators.json` entry, exactly as `gf180tcad.docgen` has none. If a later task commits an explainer artefact (for example an idealised-example data file too slow to compute at build time), it follows the `renders` precedent: a separate top-level `explained` section (`module_list`, `extra_files`, `tree: "explained"`), read only by `gf180tcad.explain`, never in `entry_points` or `trees`, with a test that it changes no TCAD hash (`test_explained_section_changes_no_tcad_hash`) and a regeneration test that rewrites the artefact byte for byte. No task of this plan needs it.

**Decision: textbook constants have one home.** The renders plan's Task R1a creates `data/render/display.toml` for display-only physical values (the silicon band gap, the Si/SiO₂ band offsets), each with a literature source. The explainer needs the same band gap. Whichever task lands first creates the value; the explainer reads `silicon.band_gap_ev` and the offsets from `data/render/display.toml` when that file exists, and holds in `data/explain/textbook.toml` only values the renders do not use (effective densities of states, the electron affinity if a page uses it). `tests/test_explained.py::test_no_textbook_value_twice` fails when a key is defined in both files. If R1a has not merged when Task E2 needs the band gap, E2 creates `data/render/display.toml` in R1a's schema (`[silicon] band_gap_ev`, `source`, `display_only` statement) and comments on #43 so R1a builds on it.

**Decision: one reader module, `gf180tcad.quantity`.** The readers (JSON key path, CSV column with a row selector, TOML key, `canonical_sha256`) live in `src/gf180tcad/quantity.py` (standard library and numpy only, no `bpy`, no `gf180tcad.tcad` import), used by both `gf180tcad.explain.numbers` and `gf180tcad.render.manifest`. This PR edits the renders plan's Task R1a to say so, and adds `gf180tcad.quantity` to the render generator's shared module list (`generators.json` `renders.shared_modules`, renders plan Task R2b), so a reader change re-hashes every render, as it should. Whichever of E0 and R1a starts first creates the module; the other extends it. Never two reader implementations.

**Decision: formulas in two modules, for a stated reason.** The renders' formulas live in `gf180tcad.derive` (renders plan Task R1a, as edited by this PR), which is in every render's generator hash. The explainer imports the formulas it shares with the renders (the Boltzmann densities, the band edges) from there and defines none of them again. Its idealised-example formulas (mass action, Boltzmann Fermi level, built-in potential, depletion width, oxide capacitance, flat-band and threshold voltage) live in `gf180tcad.explain.idealised`, outside the render hash. The reason: a formula added to `gf180tcad.derive` changes every committed render's generator hash and stales every render (renders plan Task R4: 1–3 h of render time per device), for a formula no render uses. `tests/test_explained.py::test_no_formula_twice` fails when a function name or docstring equation appears in both modules.

**Decision: the reader.** The named reader of every explainer page is a newcomer: someone who knows basic circuits (Ohm's law, a capacitor, a transistor used as a switch) and high-school physics, has never studied semiconductor physics, and has followed a link to this project, often on a phone. They want to understand what the repo simulates well enough to read a results page. The opening sentences of each page name this reader and the one question; the pages assume nothing beyond the earlier pages of the section, which each page links where it builds on them.

**Decision: no front matter.** The site's house decision is no front matter (`tools/docs_lint.py --no-front-matter` in `tests/test_doc_measure.py` and `CONTRIBUTING.md`). The explainer pages follow it; each page's type and reader are stated in its scope sentences and in the PR body.

**Decision: textbooks added to the literature page.** Tier 2 and 3 need a MOS-device textbook beside Sze and Ng. Task E0 Step 1 adds them to `docs/limitations/literature.md` under a new heading "Textbooks for the explainer pages", each only after its record is fetched (publisher page or Crossref by DOI or ISBN) and its chapter titles are read from the table of contents of the edition cited. Candidates, all **to be fetched before use**: Tsividis and McAndrew, *Operation and Modeling of the MOS Transistor*, 3rd ed., Oxford University Press; Pierret, *Semiconductor Device Fundamentals*, the 1996 Addison-Wesley edition; Taur and Ning, *Fundamentals of Modern VLSI Devices*, 3rd ed., Cambridge University Press. The same holds for every chapter of Sze and Ng that `literature.md` does not list (it cites ch. 1, 2 and 3; the pages also need ch. 4, the MIS capacitor, and ch. 6, the MOSFET): fetched and checked against the 3rd edition's table of contents before a page cites it.

**Decision: Tier 3 is written now.** The MOSFET pages are written from the committed SPICE reference, which exists for every geometry, and are extended with the TCAD results as the MOSFET phases commit them, through the hook of Task E5. Spec §10.2 lists the MOSFET tier "with the MOSFET phases"; the plan reads that as "extended with", not "waits for" (open question 3). A candidate whose record cannot be fetched is not cited, and the page that needed it cites Sze and Ng's chapter on the same topic or leaves the value out and files an issue.

## Page list

Every page lives in `docs/explained/`, is an explanation, and opens with the device diagram from the one source model, its subject highlighted. "Drawn from" is the set of committed files the page's numbers and figures come from; the page names them in its sentences with `{repo}` links (the build fails on a missing path) and `tests/test_explained.py::test_sources_exist` checks the registry's paths on the host.

### Tier 1: basics

| Page | Question |
|---|---|
| `silicon-and-carriers.md` | What are electrons, holes and dopants, and how many are in this process's silicon? |
| `bands-and-fermi-level.md` | How does a band diagram show where the carriers are? |
| `pn-junction.md` | Why does a depletion region form where n-type meets p-type silicon? |
| `transistor-parts.md` | What are the well, source, drain and gate of a GF180MCU 5 V transistor? |
| `oxide-and-poly.md` | What are the gate oxide and the poly-silicon gate, and why do their properties matter? |

- **Silicon, doping and carriers.** Sources: Sze and Ng ch. 1 (carrier statistics, mass action), cited as textbook. Numbers: the committed intrinsic density `constants.n_i_cm3` at `constants.t_k` and `constants.n_i300_cm3` (`per_area.meta.json`); the body doping start `param.ndep_cm3` and calibrated `stack.n_ch_cm3`; gate doping `param.ngate_cm3`; source and drain peak `param.sd_peak_cm3`; the minority density in the body by mass action (idealised, `idealised.mass_action`). Figure: net doping against depth through the 1D stack (poly, oxide, body) on a log axis with the intrinsic density as a line, from the committed stack, drawn with the existing `plots.Panel` log axis. Grounding asset: the committed 1D stack; R1 (renders plan) later replaces the stack diagram with its poster still. Gap section: the TCAD uses Boltzmann statistics with a constant intrinsic density (the committed constants), and the gate at 10²⁰ cm⁻³ is degenerate, which the flat-band offset absorbs (`data/process/nfet_05v0.toml`, `param.dv_fb_v.note`).
- **Energy bands and the Fermi level.** Sources: Sze and Ng ch. 1 (textbook). Numbers: band gap (textbook, `data/render/display.toml`), the Fermi level of the body and of the gate relative to the intrinsic level by `idealised.boltzmann_fermi` from the committed dopings and `constants.vt_v` (idealised, labelled). Figure: two flat band diagrams side by side, the n⁺ poly gate and the p body of the nfet, with the Fermi level drawn at the computed position. Grounding asset: R1's band diagram frame at flat band once committed; the plain diagram until then. Gap section: Boltzmann statistics place the gate Fermi level inside the conduction band at 10²⁰ cm⁻³; the page states that this is where the simple formula stops holding, with the process file's note as the evidence.
- **The pn junction and its depletion region.** Sources: Sze and Ng ch. 2 (built-in potential, depletion approximation), Shockley 1949 (`lit-shockley`) for the diode law. Numbers: built-in potential and zero-bias depletion width of an idealised abrupt junction with this repo's source/drain peak and body doping (`idealised.built_in_potential`, `idealised.depletion_width`, labelled idealised); the junction depth `param.xj_um`. Figure: the abrupt-junction charge, field and potential panels, computed from those inputs. Grounding asset: the 2D cell's source/body junction in `figures.cross_section(highlight="junction")`; R2 later. Gap section: the 2D cell's source and drain are an analytic profile with a lateral straggle (`stack.py` docstring), not an abrupt step.

## Risks, each with what settles it

- **MyST substitutions in tables and captions.** MyST replaces `{{ }}` in inline text; a substitution inside a figure caption or a table cell may render differently. *Settled by* E0 Step 5 (one table and one caption with substitutions, checked in the HTML). *Mitigation:* the figure module writes captions with the value already in them; a table is generated by `explain` and included with `{include}` from `docs/_generated/explained/`.
