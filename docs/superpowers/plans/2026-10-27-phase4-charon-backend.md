# Phase 4: Charon backend and devsim cross-comparison — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run every TCAD job on two independent simulators, DEVSIM and Charon, from one backend-neutral device description, and cross-compare the results job by job within the numerical-acceptance tolerances of spec §5.2 (1 % on relative quantities, 2 mV on voltages, an absolute floor from the mesh-convergence noise floor). First the Charon sandbox image, then the Charon backend behind the Task 15 seam, then the 1D MOS capacitor on Charon for both devices, then the 2D MOS capacitor, then the hooks that make every Phase 3 MOSFET run on both backends from its first result. Each task ends in a reviewed, merged PR that leaves `main` standing on its own.

**Architecture:** Charon 2.2.0 (the latest public release; GPL-3.0-or-later, run in a container, spec §3) is built from Sandia's official source tarball against the Trilinos commit its manual pins, in two reproducible images on ghcr.io: `gf180-tcad-charon-libs` (Trilinos + Charon, hours to build, rarely changes) and `gf180-tcad-charon` (the dev-HEAD TCAD image plus a copy of the Charon install and a hash-locked `netCDF4`, minutes to build). Charon has no 1D mode and reads only Exodus II meshes, so the backend writes the device description's mesh as Exodus without moving a node (a pseudo-1D quad strip for the 1D stack; the gmsh triangles as TRI3 blocks in 2D), writes a Charon input deck with the project's constants and models, runs `charon_mp` single-rank and single-threaded through `tools/sandbox-run --network none`, and parses the outputs back into the same result file layout as the DEVSIM backend. Charon results live in a parallel tree `results/tcad-charon/`, the comparison files in `results/tcad-compare/`; the DEVSIM trees under `results/tcad/` keep their paths and bytes. A new comparison module holds the tolerances once, importing the mesh-convergence criterion, and the agreement page is generated from the comparison files only.

**Tech Stack:** Charon 2.2.0 (`charon-distrib-v2_2.tar.gz`), Trilinos `81e9581a3c5f701d41e6828d0f0e5affcef5373a` (2022-05-16), TriBITS `769f615fafb`, OpenMPI 4.x, netCDF 4.x, HDF5 1.10+, Boost 1.71+, CMake ≥ 3.23.1, GCC (C++14), netCDF4 1.7.5.1 (Python, Exodus I/O), meshio 5.3.5 (read-back cross-check only), plus the Phase 2 stack (DEVSIM, meshwell, gmsh, gdsfactory, gf180mcu, CPython 3.13, uv, pytest, Sphinx/MyST, Docker/BuildKit, GitHub Actions, ghcr.io). ## Global Constraints

All Phase 2 Global Constraints apply unchanged (licences, git rules for both repos, sandbox, SPICE provenance frozen, host-vs-image split, determinism, physics constants, result files, public data, documentation links, submodule hygiene, hosted CI only). In addition:

- **Charon is GPL-3.0-or-later, run only in a container.** No Charon binary enters this repo or the fork, and no Charon source except the patches under `docker/charon-libs/patches/`, which quote Charon lines and are therefore derivative works: each carries `# SPDX-License-Identifier: GPL-3.0-or-later` and a header naming the file it patches, and `docker/charon-libs/README.md` plus the repository's licence notes state that these files are GPL and not under the Apache-2.0 grant. The build inputs are fetched by sha256 at image build time and mirrored on the input mirror. Publishing the image on ghcr.io distributes GPL binaries, so the corresponding source is provided: the input mirror release (`gf180-tcad/inputs/charon-<date>`) holds the exact Charon and Trilinos tarballs, the patches and the opts file, the image's `org.opencontainers.image.source` label and `docs/reproduce/image.md` point at it, and `/opt/charon/share/gf180tcad/SOURCES.json` inside the image lists the same files with their sha256. gf180-tcad code stays Apache-2.0; fork code MIT. The Charon input decks the backend writes are data, generated at run time, never committed except as test fixtures (small, in `tests/charon/fixtures/`).
- **One device description, two backends.** `backends/charon.py` consumes only the public API of `gplugins/devsim/device_description.py` (Task 15), never `backends/devsim.py` or DEVSIM itself. A model, constant or contact type the description carries that Charon cannot express identically is **refused** by the backend with `NotComparable(reason)`; the job is then written with `comparable: false` and the reason, never approximated (spec §12.1).
- **Physics parity is pinned in code.** The constants table of the Phase 2 Global Constraints is written into every Charon deck explicitly: `relative permittivity = 11.7` / `3.9`, `lattice temperature = 298.15`, `constant intrinsic concentration = 8.265841554853887e9` (or the equivalent `Effective DOS` + `constant bandgap` pair, whichever Experiment B2 shows the drift-diffusion path honours), `fixed mobility for electrons is 1417 holes is 470.5`, `electron lifetime is constant = 1e-5` and the hole counterpart, Boltzmann statistics (Charon's default; the deck never enables Fermi–Dirac, band-gap narrowing or incomplete ionisation). Charon's hard-coded `q`, `kb` and `eps0` differ from the project's CODATA 2018 values by 9.2e-8, 1.1e-6 and 4.7e-10 relative; the image applies a two-line patch to `Charon_Physical_Constants.cpp` (Task A, committed as `docker/charon-libs/patches/0001-codata2018-constants.patch`, sha256 in `versions.json`), so both backends compute with the same constants. The effect of the unpatched values (29 nV on k_B·T/q, 4.7e-10 relative on C_ox) is recorded on the limitations page for scale.
- **Identical mesh means identical node coordinates.** The Charon Exodus mesh is written from the device description's node coordinates in µm (the plugin's unit; DEVSIM receives them × 1e-4 in cm). A test round-trips every node: `x_charon_um == x_devsim_cm / 1e-4` within one ulp, and the element connectivity is a permutation-free copy. No smoothing, reordering, merging or re-meshing anywhere in the backend.
- **Single rank, single thread.** `charon_mp` runs without `mpirun` (one rank, as Xyce does in the base image), Kokkos serial, `OMP_NUM_THREADS=1` inherited from `tools/sandbox-run`, OpenBLAS pinned by `OPENBLAS_CORETYPE` from the base image. A direct sparse solver (Amesos2 KLU2) is the reference linear solver when the Charon syntax allows it (Experiment B3); otherwise Belos GMRES at a 1e-12 tolerance with a fixed restart length, single rank, which is deterministic in iteration order. Two runs must give byte-identical result files; the `crosscheck-charon` job checks a GitHub-hosted runner against the manifest. If Charon proves non-deterministic across hosts, its trees are compared numerically with a stated tolerance and the docs say so (spec §9 fallback), but never silently.
- **Results layout (decided here, spec §12.1 "the exact layout is fixed in the plan").** The DEVSIM trees keep their paths and bytes under `results/tcad/`. Charon results mirror them under `results/tcad-charon/` with the same tree names (`moscap1d`, `moscap2d`, `meshconv`, later `calibration` and `validation`), one `provenance.json` per tree root, the same file names and columns, and a `backend` key in every meta file (`"backend": "charon"`). The DEVSIM meta files gain `"backend": "devsim"` only when a tree is next regenerated for another reason (issue #35 for 2D); until then the reader (`gf180tcad.tcad.moscap1d.read`, `moscap2d.read_cv`) defaults a missing key to `devsim`, which a test asserts. Comparison files live in a third root, `results/tcad-compare/<tree>/<device>/<params>[/<gid>]/compare.json`, with one `provenance.json` per tree root. **No existing tree is moved, regenerated or restamped by this layout.**
- **Per-tree generators (PR #50 scheme, extended) and the registry out of the closures.** Today the registry (`TCAD_GENERATORS`, `TREE_GENERATORS`, `IMAGES`, `CALIBRATION_DIR`) lives in `src/gf180tcad/tcad/__init__.py`, which is in **both** entry points' closures, so adding a Charon entry point, a tree row or an image name there would change all five DEVSIM hashes, and `image_ref("charon")` would raise `KeyError`. Task B0 therefore moves the registry into a data file, `src/gf180tcad/generators.json` (entry point → sorted module list; tree root → entry point; image name → pin file and `versions.json`; tree roots per backend), read by `gf180tcad.tcad` at run time and **not hashed** (it decides what is hashed; the AST import-graph test keeps each module list exact, so an entry that drops a module fails the test instead of silently changing a hash). After B0, two new entry points, `gf180tcad.charon.__main__` (writes `results/tcad-charon/*`) and `gf180tcad.compare.__main__` (writes `results/tcad-compare/*`), are added as data; `gf180tcad.tcad.__main__` and `gf180tcad.calibrate.__main__` never import `gf180tcad.charon` or `gf180tcad.compare`, and the calibrate code is never edited for Charon (the simulator is injected, Task B0), so a Charon or compare code change never changes a DEVSIM tree's hash. The hashed plugin files are per generator too: the DEVSIM and calibrate generators hash `third_party/gplugins/gplugins/devsim/**` **minus** `gplugins/devsim/backends/charon/**`; the Charon generator hashes all of it. **Every DEVSIM hash change is named by the task that causes it:** B0 (the registry move and the exclusion are code changes in `gf180tcad.tcad`: one restamp of the five trees, recorded on `docs/reproduce/index.md` like PR #50's, with `make reproduce-quick` proving the 1D data unchanged) and F (the fork's `device_description.py` is in the hashed plugin files of every generator: the cheap trees, 1D, calibration and validation, are regenerated and compared byte for byte, the 2D trees restamped and recorded). No other task touches a DEVSIM closure; `tests/tcad/test_tcad_provenance.py::test_committed_tcad_provenance_current` enforces it.
- **Tolerances live in one module.** `gf180tcad.compare.tolerances` holds `RELATIVE = meshconv.CRITERION` (imported, not repeated), `VOLTAGE_V = 2e-3`, and `floor(scale, rel_tol) = meshconv.NOISE_K * rel_tol * scale`. `tests/test_doc_numbers.py` ties the numbers on `docs/comparison/agreement.md` (numerical acceptance) and `docs/comparison/backends.md` to the module. The tolerance is never loosened to make a job pass; a failure is recorded on the limitations page with its numbers and an issue (spec §12.1 "On disagreement").
- **Host budget.** This host has 31 GiB; the 8 GiB session scope plus all containers must stay under about 24 GiB, so containers (jobs and image builders together) get about **16 GiB**. Charon 1D jobs are 2 GiB; Charon 2D jobs 16 GiB, **one at a time** (`--jobs 1`), never concurrently with a DEVSIM 2D job or an image build. The Trilinos build runs in a memory-limited BuildKit builder (`GF180TCAD_BUILDER`, as `docker/tcad-dev/build` allows) with `-j2` and `MemoryMax=16G`, nothing else in the sandbox meanwhile; compile jobs of Panzer and MueLu peak at several GiB each, and a job that is killed is a reported failure, never a reason to raise the cap. Parallel `make` does not change the produced bits (only the link order, which make keeps fixed), so "single-threaded" is a run-time rule, not a compile-time one; the `rebuild` CI job proves the bits.
- **Where things run.** Charon image builds, all 2D Charon jobs and the first Charon calibration run locally. GitHub-hosted runners rebuild the thin `charon` image on every image change, rebuild `charon-libs` only on schedule or dispatch (6 h job limit, Risks), and rerun the 1D calibrated Charon jobs plus their comparison files in `crosscheck-charon`.

## Review Focus

- **Docs updated in the same PR (2026-10-27).** Every review checks that the PR updated the status pages it affects (README Status, the `docs/index.md` Status, this plan's checkboxes, the limitations index, the affected results and comparison pages) at the same time; a PR whose docs lag is "needs fixes" (CONTRIBUTING.md, PR checklist).
- **Same inputs, really.** A reviewer must be able to diff the Charon deck's constants, doping, contacts and bias plan against the DEVSIM job's `*.meta.json` and find no difference other than syntax. The deck is committed as a test fixture for each device; a test regenerates it and compares byte for byte.
- **C–V method parity.** The Charon quasi-static C–V must be the same central difference as DEVSIM's (`DV_QS = 1e-3` V around each committed `vg`), on charges obtained from the converged zero-current drift-diffusion state at the identical biases, extracted as a conservative control-volume flux, not from Charon's single-Fermi-level `nlp` solve with a biased poly gate and not a different-frequency small-signal curve. The harmonic-balance path is a fallback for 2D AC only, at the same 1 MHz as DEVSIM's `cgx.csv`. Reject any pairing of a Charon small-signal curve with a DEVSIM quasi-static one.
- **Units.** Charon: coordinates µm, doping cm⁻³, 2D currents per cm of depth, capacitance per cm of depth; the pseudo-1D strip divides by its width in cm to give F/cm²; the project reports fF/µm². Every conversion has a unit test with a hand value (C_ox(16.05 nm) = 2.152 fF/µm² at ε_ox = 3.9).
- **No silent non-convergence.** A LOCA step that fails, halves and retries, or a Newton solve that stops at a relaxed tolerance, fails the job unless the point is recorded with its tolerance in the meta, as the DEVSIM backend records `extended_fallback` and `roundoff_accepted`.
- **One backend is never preferred.** The comparison file carries both values and the verdict; docgen renders both curves; a disagreement is a `numerics` entry on the limitations page plus an issue, never a dropped backend or a wider tolerance.
- **Calibration leakage** rules of Phase 2 apply to the Charon backend as well: Charon validation geometries are computed only after the parameters are frozen, with the same `CalibrationLeak` guards.

**Decision: C–V method on Charon.**
- **Primary, `method="qs"`: zero-current drift-diffusion solves at `vg ± dv_qs`, central difference of the gate charge, exactly DEVSIM's definition.** `drift diffusion cvfem` in every semiconductor block (poly gate and body), `laplace cvfem` in the oxide, every non-gate contact fixed at 0 V and the gate ohmic contact on the poly swept: with no current path, the steady state is the equilibrium state of each region at its own contact potential, which is what DEVSIM's quasi-static sweep solves (the plugin's `cv.py` gives each silicon region its own quasi-Fermi level, "phi … Vg for a poly gate"). Charon's nonlinear-Poisson (`nlp`) solve is **not** the primary method: manual §1.1 derives it for one equilibrium Fermi level everywhere (E_Fn = E_Fp = 0) and §3.4's example has every contact at 0 V, so a biased semiconductor gate would get the wrong poly carrier density; upstream's `pmoscap` avoids the question with a metal `contact on insulator` gate, which this project does not use. `nlp` may be used only if Experiment B2 shows, against the drift-diffusion result, that it honours a biased semiconductor gate (every bias within 1e-9 relative in the gate charge); even then it is a speed option, recorded in the meta as `charon.equilibrium_solve`. Mobility and lifetimes enter the deck but not the result; the deck carries the constant values for parity. Two LOCA sweeps per job, each with a fixed step equal to the committed `vg` grid spacing: sweep A from `vg[0] − dv` to `vg[-1] − dv`, sweep B from `vg[0] + dv` to `vg[-1] + dv` (`start sweep options` with `initial = minimum = maximum step size`, `maximum number of steps`), both starting from one converged state file at `vg[0]`. Every state is written to the output Exodus file (`Unscale Variables is on`); the gate charge per unit depth at each state is the **discretely conservative CVFEM face flux** of the oxide's Laplace equation through the control-volume faces that separate the oxide from the poly/oxide interface nodes (equivalently, the assembled Laplace residual at those interface nodes with only the oxide side assembled), computed by `parse.py` from the nodal potential with Charon's own control volumes, **not** an element-gradient flux, which is not conservative on a triangle mesh; in the 1D strip it reduces to `ε_ox·Δψ_ox/t_ox` per unit width. Experiment B6 checks the extraction: on the 1D strip and on the 2D uniform stack, the flux at the poly/oxide interface equals the flux at the oxide/body interface within 1e-10 relative (charge conservation across the charge-free oxide) and the total space charge of poly plus body integrated over Charon's control volumes equals minus the gate charge within 1e-9. `C_i = (Q_B,i − Q_A,i)/(2·dv)`, divided by the strip width in cm for 1D (F/cm² → fF/µm² by `1e7`, the existing helper) or by the drawn L for 2D as `moscap2d` does. The grid alignment of the two sweeps is asserted from the `gate_Voltage` column of `currents-loca.dat` (every entry within 1e-12 V of `vg ± dv`); a LOCA step that is cut fails the job. Why not one sweep at step `dv`: 10,001 states for the ±5 V grid. Why not a per-point pair of runs: 402 process starts, each reading the mesh and setting up the problem again; negligible in 1D, an overhead to be measured in 2D (Experiment E1 times one start-up at 200k nodes) and avoided by design.
- **The hard range, and the fallback.** The plugin's `cv.py` records why DEVSIM solves QS with Poisson–Boltzmann: drift-diffusion with only a body contact does not converge at the onset of inversion when Newton is stepped from depletion (the inversion charge has no current path and must appear through the recombination terms, a stiff step for the continuity equations). Charon's zero-current DD sweep faces the same range, so Experiment B2 tests **exactly it**: the sweep through the depletion-to-inversion transition (nfet u from +0.3 to +1.5 V, pfet mirrored, at the calibrated doping), stepped from depletion in the committed grid order, with the LOCA step failures and Newton iteration counts recorded per point. **Fallback, used for any point LOCA cannot pass, or for the whole job if B2 shows the sweep cannot be done:** per-point pairs of steady-state runs at `vg ± dv` whose initial guess is the converged state of the **previous grid point on the same side** (`Import State File <previous>.exo at Index -1`, so the Newton start is the nearest converged solution, never the equilibrium state at `vg[0]`); if that still fails in the hard range, the point is reached through intermediate sub-steps from the previous state (halving the voltage step, each sub-state imported by the next), the number of sub-steps recorded in the meta as `charon.substeps` per point; the solved point is always exactly `vg ± dv` at the full tolerance, and a point that cannot be reached fails the job. Same charge extraction, never cheaper in grid or tolerance.
- **2D AC (`cgx.csv`, 1 MHz): harmonic balance small-signal** (`apply harmonic balance for small signal analysis`, `small signal sweep from … with amplitude 1e-4` on the gate, `frequencies "0"` on the others), the gate frequency `1e6`, at every `AC_STRIDE`-th bias as DEVSIM. `C_xg = I_x,cos/(2π f·A)` from the `*_CosH1.000000__DispCurrent` plus conduction `*_CosH1.000000__Current` columns of each non-gate contact (the quadrature component of the total small-signal current; Experiment B4 fixes the sign and which columns sum, checked against the analytic parallel-plate case). The charge-conservation check (Cgg = Σ Cxg within 0.1 %) applies as in DEVSIM.
- **Not used:** a low-frequency harmonic-balance curve as a stand-in for QS. With only a body contact the inversion charge responds on τ_gen ≈ τ·N_A/n_i ≈ 10² s, so an "LF" small-signal curve is the HF curve unless f ≪ 1e-2 Hz; that is a different physical quantity from DEVSIM's QS and would be a mismatched pairing (Review Focus).

## Risks and open questions (spec §12.1), with the experiment that settles each

- **Build cost and runner limits (open question "Build cost").** Estimate 2–4 h Trilinos + 0.5–1 h Charon at `-j4`, 10–20 GB build tree, several GiB per compile job; GitHub-hosted runners: 4 vCPUs, 16 GB, ~14 GB disk, 6 h per job. *Settled by* Experiment A1 (timed local build) and the first `workflow_dispatch` rebuild of `charon-libs` on a runner. *Mitigation:* the two-image split; the `charon-libs` rebuild gated to schedule/dispatch; if it cannot finish on a runner, the Trilinos stage is reproduced locally only and the docs say so (a §9 deviation, listed in limitations), while the thin `charon` image and every Charon result in `crosscheck-charon` stay runner-verified.
- **Bit-reproducible build.** A reproducible image needs identical binaries from two builds: `SOURCE_DATE_EPOCH` for `__DATE__`, deterministic `ar`, `-ffile-prefix-map`, no `-frecord-gcc-switches`, no build-time absolute paths baked by CMake into installed files (Trilinos writes `*Config.cmake` with paths: either keep them identical by building in a fixed path, or strip them from the install). *Settled by* the `rebuild` CI entry (identical `IMAGE_ID`). *Fallback:* record the layer digests of the one local build and verify the rebuild by `charon_mp.exe` sha256 and the nightly-test outputs instead; documented.
- **Compiler drift.** Trilinos 2022 under the base image's GCC 13 (C++14 mode) may need header fixes. *Mitigation:* numbered patches, each with a reason; never `-fpermissive`; or the GCC 14 debs of the dev image if GCC 13 cannot be made to work (then recorded).
- **Trilinos version versus the "latest" rule.** Charon 2.2.0 pins Trilinos `81e9581` (2022-05); Trilinos 17.2.1 (2026-08) is expected not to build Charon 2.2.0 unmodified (four years of Panzer, Kokkos and Tpetra API changes), but that is **untested** and is settled by Experiment A1b, a one-hour configure attempt whose outcome is recorded either way. The spec's rule ("the latest Trilinos it builds against") is satisfied by the pin.
- **Mesh conversion fidelity (open question "Meshing and input format").** Node identity is by construction (the writer copies arrays). The risk is Charon's element support: quads are "preferred"; TRI3 unverified. *Settled by* Experiment B1. *Fallback:* 2D on Charon's own quad mesh at the same `MeshSpec` sizes, `comparable: false` (`tri3-unsupported`), the matrix says so.
- **2D mesh identity across images.** The committed DEVSIM 2D meshes come from the stable image's gmsh 4.15; the Charon image inherits the dev image's gmsh 5, which meshes the cells differently, and the output cache may not feed a generator (§9.1). Task E therefore waits for #35 (DEVSIM 2D on the dev image) and the Charon job asserts the committed `mesh_sha256` before solving. *Settled by* `test_job_refuses_unexpected_mesh_sha` and the committed compare files' `identical_inputs.mesh`.
- **Physics-model parity (open question "Which physics models").** Constants: Charon's `q`, `kb`, `eps0` are hard-coded and differ at ≤ 1.1e-6 relative; patched in the image (Task A), effect size recorded. n_i: `constant intrinsic concentration` or `Effective DOS` + `constant bandgap`; which one the NLP path honours is Experiment B2, verified by the bulk n·p product. Boltzmann in the degenerate poly: Charon's default; the deck never enables Fermi–Dirac. Constant mobility: `fixed mobility` (interpreter syntax confirmed). SRH with given lifetimes: `Carrier Lifetime Block`, constant. Defaults that must be overridden and are: permittivity 11.8, affinity 4.17 eV, band gap 1.08 eV. The discretisation errors differ (FV Scharfetter–Gummel vs CVFEM/FEM): that is what the 1 % and the per-backend mesh convergence measure.
- **Quasi-static C–V on Charon (open question "C–V method").** Primary: NLP + LOCA two-sweep central difference on the oxide displacement flux. *Settled by* Experiment B2 (NLP sweepable?), `test_qs_matches_exact_poisson_boltzmann` (0.1 % against the exact 1D solution) and `test_qs_equals_devsim_1d`. *Fallback:* drift-diffusion sweeps with all other contacts at 0 V. *Never:* a low-frequency small-signal curve as a QS stand-in.
- **Absolute floor (open question "Absolute floor").** For the quasi-static C–V, `NOISE_K · rel_tol · scale` with `scale` the sweep's largest |C| (1e-6 of the scale at the reference tolerances), because `NOISE_K` is derived for exactly that central difference. For AC capacitances (Task E) and currents (Task F) the floor is derived separately before use; the module refuses an underived kind. *Settled by* `test_near_zero_uses_floor`, `test_underived_floor_kind_raises`, and by measuring both backends' own noise (rerun at ten times tighter tolerances; the differences must be below the floor), recorded on the backends page.
- **Calibration (open question "Calibration").** Charon runs at DEVSIM's frozen values for every comparison; an independent Charon calibration is committed and shown, not used. If the two calibrated sets differ by more than the tunables' own fit uncertainty (reported by `least_squares`), that is a `numerics` finding on the limitations page.
- **2D run time (open question "2D run time and memory on this host").** Unknown until Experiment E1; one 16 GiB job at a time either way, so 2D machine time at least doubles. *Mitigation:* order L_min first; resume from state index on a cut sweep; never a cheaper grid.
- **Determinism across hosts.** Single rank, serial Kokkos, OpenBLAS pinned; the Exodus header may carry a date (never committed; stripped from the writer's own files). *Settled by* `test_two_runs_byte_identical` and `crosscheck-charon`. *Fallback:* numerical comparison with a stated tolerance for Charon trees only, documented (spec §9).
- **Task 15 interface drift.** The seam is being implemented in parallel. Task B starts only from the merged seam; its first step is to diff this plan's assumed fields against `device_description.py` and update the plan's Interfaces paragraph in the same PR.
- **Provenance churn.** The registry in `gf180tcad.tcad` and the plugin files under `gplugins/devsim/` are in every closure; without Task B0 every Charon change would restamp the DEVSIM trees.
