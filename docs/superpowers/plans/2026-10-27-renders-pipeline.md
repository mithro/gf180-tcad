# 3D renders of the simulated processes and the reduced mesh artefact — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give every simulation process in the documentation a good-looking, high-quality 3D render (Blender, Cycles, CPU only) that shows what is simulated and what happens during it, may simplify and exaggerate, and takes every number from a committed file, with the source, value and scale factor of each quantity recorded in a render manifest that a test re-reads. On the way, settle issue #39: a committed reduced mesh artefact per 2D job, cut from the full gmsh mesh by a reduction generator and tied to the job's committed `mesh_sha256`, which feeds the 2D render, the mesh-convergence render and a flat mesh figure on the 2D docs pages. Each task ends in a reviewed, merged PR that leaves `main` standing on its own.

**Owner's words** (spec §16, 2026-10-27): "we should include good looking, high quality 3d renders (probably using blender 3d) of all various simulation processes in the documentation which allows a person to see and understand what is being simulated and what is happening. These renders can simplify or exadurate the real world results (making diagrams not to scale, etc) but should still be based on the actual numbers."

**Architecture:** Three new committed trees and one new image, each with its own writer entry point and per-tree hash (the PR #50 scheme, with the registry as data after Charon plan Task B0). (1) `results/tcad/meshes/<image>/`: the reduced mesh artefacts, written in the TCAD image by `gf180tcad.meshcut` from a full `mesh.msh` that the host command pulls from the output cache by `mesh_sha256` (or regenerates in the sandbox) before the `--network none` run; the only generator that reads the cache (spec §9.1). (2) `results/tcad/profiles1d/` and `results/tcad/calibration-history/`: the two quantities the renders need that cannot be derived from committed outputs (the 1D potential and carrier profiles at every committed bias; the optimiser's evaluation history), each written by its own new entry point that re-runs the committed job and proves it re-ran the same job by reproducing the committed C–V (or calibration result) byte for byte, so no existing closure, tree or hash changes. (3) `results/renders/<process>/`: PNG stills and VP9 WebM animations, each with `<render>.render.json` (every quantity: source file, key path or CSV selector, unit, value, scale factor, derivation) and `<render>.scene.json` (the scene description Blender reads), written by `gf180tcad.render` in two steps: a host-side scene builder (pure Python, no physics beyond recorded derivations) and a sandboxed Blender run in `ghcr.io/mithro/gf180-tcad-render` (official Blender 5.2.3 LTS, archive sha256 pinned, Cycles CPU, fixed seed, sample count and threads). The docs build only copies and embeds committed files; it stays offline and never runs Blender or an encoder.

**Tech Stack:** Blender 5.2.3 LTS (`blender-5.2.3-linux-x64.tar.xz`, 385,331,224 bytes, sha256 `78486c018b4443efe5e75ab54c290ed8c15abafd249b862c2c9ce2530a918eec`; GPL-3.0-or-later as distributed), its bundled Python, numpy and FFmpeg (WebM container, VP9 codec), Cycles on CPU; the Phase 2 stack (DEVSIM, gmsh, meshwell, gplugins fork, CPython 3.13, uv, numpy, matplotlib for the colour-map tables, pytest, Sphinx/MyST, Docker/BuildKit, GitHub Actions, ghcr.io). Versions are the latest LTS at plan time (2026-10-27); re-check at pin time (Task R2a) and take the newest 5.2.x point release.

## Global Constraints

All Phase 2 and Phase 4 Global Constraints apply unchanged (licences, git rules, sandbox, SPICE provenance frozen, host-vs-image split, determinism of results, result files, public data, documentation links, per-tree generators, registry as data, host budget, where things run). In addition:

- **Based on the actual numbers, mechanically.** No number is typed into a scene builder or a Blender script. A scene builder reads committed files only through the `Quantity` readers of `gf180tcad.quantity` (the one reader module, shared with the explainer pages of `docs/superpowers/plans/2026-10-27-explainer-docs.md`; `gf180tcad.render.manifest` imports them) (JSON key path, CSV column with a row selector, npz array name, TOML key), and every value it uses is a manifest entry; `tests/test_renders.py` re-reads every entry from its named source. Styling constants (colours, light intensities, camera angles, font sizes, label offsets) live only in `render/style.toml` and are not quantities. Display-only physical values that no simulation uses (the silicon band gap and the Si/SiO₂ band offsets for drawing band edges) live in `data/render/display.toml` with a literature source per value and the statement "display only: not an input to any simulation"; they are manifest entries like any other.
- **Derivations are recorded, not hidden.** A derived quantity's manifest entry names its formula as a string from a closed table in `gf180tcad.derive` (the renders' formula module; the explainer pages import the formulas they share with it and keep their own idealised-example formulas in `gf180tcad.explain.idealised`, outside the render hash) (`band_edge_ec`, `band_edge_ev`, `boltzmann_n`, `boltzmann_p`, `depletion_edge`, `sheet_charge`, `log10_abs`, `region_boundaries`, `envelope_minmax`, `area_scale`, …), its input entries and its value; the test re-evaluates the formula from the inputs. The table's functions are pure numpy, unit-tested against hand values, and contain no solver: a render never recomputes physics a job computes.
- **Exaggeration is data.** Every geometric quantity carries `scale` (1 when to scale); every render has an `exaggeration` list (`"oxide thickness ×40"`, `"depth axis log-scaled from 1 nm"`) generated from those entries, and the same strings are drawn into the image and written on its docs page by docgen. A scale factor is chosen per render kind in `render/style.toml` and is the same for nfet and pfet and every geometry (spec §10.1 camera conventions).
- **Two licences, one boundary.** `src/gf180tcad/render/` (scene builders, manifest, derivations, CLI) is Apache-2.0 and never imports `bpy`. `render/blender/*.py` (the scripts Blender runs) import only `bpy`, `mathutils`, `bmesh`, Blender's bundled `numpy` (for `foreach_set` on large meshes) and the standard library, read only the scene JSON and the committed assets it names, and carry `# SPDX-License-Identifier: GPL-3.0-or-later`, because Blender treats API scripts as part of the program (licence page above); `render/blender/README.md` and the repository licence notes say so, as for the Charon patches. An AST test enforces both directions.
- **Renders are outside bit-identity (spec §9, §10.1).** Seeds, sample counts, thread counts, tile size and denoiser are fixed and recorded; a rerun on the same host should give the same file (Experiment D1), but the pixels are never compared by hash in CI. What is checked is the manifest (values and input hashes), the scene description (regenerated byte for byte on the host) and the size budget. The new **data** trees (`tcad/meshes`, `tcad/profiles1d`, `tcad/calibration-history`) are results and **are** under bit-identity, the manifest and the cross-host check like every other TCAD tree.
- **The cache is read by exactly one generator.** Only `gf180tcad.meshcut`'s host command reads the output cache, by calling `tools/output-cache pull <sha256> --out <scratch>/mesh.msh` as a **subprocess** (so `gf180tcad.outcache` stays out of every closure; `tests/test_outcache.py` already asserts it for the TCAD entry points and is extended to every entry point in `generators.json`); the sandboxed part reads only the pulled file and checks its sha256 before use. Renders, tests, CI and docs read only committed files.
- **Provenance per tree (PR #50 scheme).** `results/tcad/meshes/{stable,dev}/provenance.json`, `results/tcad/profiles1d/provenance.json` and `results/tcad/calibration-history/provenance.json` come from `gf180tcad.tcad.tree_provenance` with their own `generator` (entry point) and image. `results/renders/provenance.json` comes from `gf180tcad.render.provenance` and records: `generator` and, **per render**, a `generator_sha256` over the shared render closure (every `gf180tcad.render` module except `gf180tcad.render.scenes.*`, plus `gf180tcad.quantity` and `gf180tcad.derive`) plus that render's own scene module plus `render/blender/**`, `render/style.toml`, `render/assets/**` and `tools/sandbox-run`. `data/render/display.toml` is not a generator file: it is a manifest input, hashed per render with the other inputs. The record also holds the render image reference and `versions.json`; the Blender version and archive sha256; and per render the sha256 of every input file its manifest names. **A source tree's `provenance.json` is not a render input** (a restamp changes it without changing data; making it an input would stale every render on every restamp); its sha256 is recorded as information only.
- **Host budget.** 31 GiB host, 8 GiB session scope, containers about **16 GiB** in total. Render jobs: `--mem 8g --cpus 8`, one at a time, **never** while a 16 GiB 2D TCAD job, an image build or a Charon 2D job runs; up to two 2 GiB 1D jobs may run beside one render job. Mesh-cut jobs from a pulled mesh: `--mem 4g`, two at a time allowed, but **never** beside a 16 GiB job (16 + 4 GiB exceeds the container budget). Mesh regeneration (`meshcut --regenerate`): `--mem 16g`, alone, like a 2D job, until Experiment M0 measures its peak. Image build: the memory-limited BuildKit builder, alone. OOM (exit 137) is a reported failure, never a reason to raise a limit.
- **Logs.** Every long command writes complete stdout and stderr to a file under the worktree's `tmp/` (never through a filter), with `set -o pipefail`; implementers report exit codes and log paths, and check the last 20 lines and output growth at every wakeup.

## Review Focus

- **Docs updated in the same PR (2026-10-27).** Every review checks that the PR updated the status pages it affects (README Status, the `docs/index.md` Status, this plan's checkboxes, the limitations index, the affected results and comparison pages) at the same time; a PR whose docs lag is "needs fixes" (CONTRIBUTING.md, PR checklist).
- **Can a reader trace any pixel's number?** Pick three labels or geometric features in each render and find, in `<render>.render.json`, the source file, key, value and scale; then open the source and confirm. A reviewer who cannot do this in five minutes rejects the render.
- **Is anything invented?** No literal number in `src/gf180tcad/render/scenes/*.py` or `render/blender/*.py` other than styling keys (test `test_scene_builders_have_no_numeric_literals` allows 0, 1, 2, -1 and indices); display-only constants only from `data/render/display.toml` with sources.
- **Does the image say what the page says?** The exaggeration strings and scale bar values in the image are the manifest's; the docs page text is generated from the same manifest.
- **The artefact is the job's mesh.** The reduced mesh artefact's `full_mesh_sha256` equals the job's committed `mesh_sha256`, and its nodes are an exact subset (bit-equal coordinates) of the full mesh's.
- **No existing hash moved without being named.** Each task's provenance impact paragraph says which hash lists change; `tests/tcad/test_tcad_provenance.py::test_committed_tcad_provenance_current` stays green.

### Task R0: reduced mesh artefact generator (`gf180tcad.meshcut`), for #39 (closed in R4)

**Context.** Spec §10.1 "Mesh pictures" and §9.1: the full 2D meshes (`mesh.msh`, gmsh MSH 2.2 ASCII, 25–62 MB, 205 k–503 k nodes) stay out of the repo; a reduction generator cuts a ≤ 2 MB artefact around the gate and commits it with provenance tied to `mesh_sha256`. The four committed start-parameter meshes are on no disk and the cache is empty. The meshes regenerate deterministically from the committed cell and `selected.json` (`docs/limitations/moscap2d.md`, "The meshes are not committed") **if** today's code on the stable image still produces the bytes the committed trees recorded; the spec expects it may not ("the committed 2D trees predate the current job format, so this is likely for all of them").

**Files:**
- `src/gf180tcad/meshcut/__init__.py` (constants: `ARTEFACT = "mesh-window.npz"`, `META = "mesh-window.meta.json"`, `MAX_BYTES = 2_000_000`, `FORMAT = 1`; region-name table), `msh.py` (a strict MSH 2.2 ASCII reader in numpy: `$Nodes`, `$Elements` (type 2 triangles, type 1 lines), `$PhysicalNames`; refuses any other version or element type), `window.py` (`gate_window(nodes, tris, regions, xs) -> Window`: the elements whose centroid lies in the window, the nodes they use, renumbered in ascending original-id order), `npz.py` (`write_npz(path, arrays)`: a deterministic zip: `ZipInfo` date 1980-01-01 00:00:00, `ZIP_DEFLATED` level 9, sorted member names, `.npy` v1.0 headers from `numpy.lib.format`, no extra fields; `read_npz` via `numpy.load`), `job.py` (the in-sandbox job: hash check, read, net doping at the window nodes, cut, write), `__main__.py` (host commands `cut` and `regenerate`; in-image `cut-job` and `regenerate-job`);
- `results/tcad/meshes/<image>/<device>/<params>/<gid>/{mesh-window.npz,mesh-window.meta.json}`, `results/tcad/meshes/<image>/provenance.json` (one per image subtree, see the decision below), `results/MANIFEST.sha256`;
- the cross-host check for the new tree, without editing `RESULTS_IMAGE` in hashed `gf180tcad.tcad`: `src/gf180tcad/manifest.py` (`tcad_axes()` builds its tree names from `RESULTS_IMAGE` today; it gains the extra tree names from the `trees` rows of `generators.json`, which is data), `tools/crosscheck-tcad-run` (takes each job's image from its tree's recorded `provenance.json` instead of `job_image`'s `RESULTS_IMAGE` lookup, for trees that are not in `RESULTS_IMAGE`), `.github/workflows/crosscheck.yml` (the path filter gains `src/gf180tcad/meshcut/**` and `results/tcad/meshes/**`), `tests/crosscheck_tcad_subset.txt` (one meshes job), `tests/test_manifest_subset.py::test_meshes_subset_parse`, `tests/test_crosscheck_tcad.py::test_registry_tree_uses_its_recorded_image`;
- `src/gf180tcad/generators.json` (data rows: entry point `gf180tcad.meshcut.__main__` with its exact module list; trees `tcad/meshes/stable` and `tcad/meshes/dev` → that entry point);
- `src/gf180tcad/docgen.py` (`_NO_MESH` replaced by `_mesh_figure(job)`: a flat SVG of the window drawn by matplotlib from the committed artefact, regions in Okabe–Ito, mesh edges at 0.2 pt; when no artefact exists for a job, a sentence naming why, never the old deviation text), `src/gf180tcad/manifest.py`. The per-image trees `meshes/stable` and `meshes/dev` join `tcad_axes()`. Their jobs are `meshes/<image>/<device>/<params>`, the directory that holds the `<gid>` subdirectories, as a `moscap2d/<device>/<params>` job does, so the files are `tcad/meshes/<image>/<device>/<params>/<gid>/*` under the manifest prefix `tcad/`. A subset line is `meshes/<image>/<device>/<params>`, for example `meshes/stable/nfet_05v0/start`. `_check_job` reads the last two parts as `<device>` and `<params>`, and the rest, joined by `/`, as the tree, which must be in `tcad_axes()`; `tcad_trees()` uses the same split, so the existing three-part lines parse unchanged. Test: `tests/test_manifest_subset.py::test_per_image_tree_job_lines`.;
- `tests/test_meshcut.py`, `tests/tcad/test_meshcut_job.py` (sandbox-marked), `tests/test_outcache.py` (extended), `tests/tcad/test_tcad_provenance.py` (the new entry point and tree), `tests/test_docgen.py`;
- `docs/limitations/moscap2d.md` ("The meshes are not committed" gains "The reduced mesh artefact": what is kept, the window, the size, the tie to `mesh_sha256`, which jobs have one and why the others do not), `docs/limitations/index.md` (the #39 deviation bullet rewritten: mesh figure exists for the listed jobs; the remaining gap, if any, stated with its cause), `docs/reproduce/output-cache.md` (the one generator that reads the cache), `docs/reproduce/index.md` (the new tree).

**Decision: format.** A deterministic `.npz` (above), not an SVG: the same artefact must feed the 3D render (R2, R5) and the flat figure, and an SVG would freeze one projection and styling into the data. Members: `nodes_um` (float64, shape (n, 2), **bit-equal** to the MSH values, so subset-ness is testable exactly), `triangles` (int32, (m, 3), indices into `nodes_um`), `region` (uint8, (m,), index into the meta's `regions` list), `node_id` (int64, (n,), the node's id in the full mesh), `net_doping_cm3` (float64, (n,), the 2D job's own analytic doping evaluated at each window node by the same `stack` functions the job uses, so the render does not recompute it), `boundary_lines` (int32, (k, 2), the window's region interfaces). `mesh-window.meta.json` (sorted keys, `repr` floats): `format`, `job` (`tree`, `device`, `params`, `geometry_id`, the source job's `cv.meta.json` sha256), `full_mesh_sha256`, `full_mesh_node_count`, `full_mesh_triangle_count`, `window` (`x_um`, `y_um` bounds and the rule that set them), `node_count`, `triangle_count`, `regions`, `npz_sha256`, `source` (`"cache"` or `"regenerated"`), `units`. Float64 coordinates cost about 45 bytes per node before deflate; Experiment M1 sets the window so the npz is ≤ 2 MB.

**Decision: window.** A rule, not a hand-picked box, stored in the meta: centred on the gate, `x` from the gate's left edge minus `k_x · L_gate` to its right edge plus `k_x · L_gate`, `y` from the poly top to `d_y` below the silicon surface, with `k_x` and `d_y` constants in `gf180tcad.meshcut` (`WINDOW_KX`, `WINDOW_DEPTH_UM`; data, not styling, so not in `render/style.toml`), chosen by Experiment M1 as the largest that fits 2 MB for the **largest** committed mesh (the L = 2 µm cells, 503 k nodes), and the same for every job. If no single rule fits the L = 2 µm cells under 2 MB, the artefact for those cells keeps two windows (`edge`: the left gate edge with the source overlap at full fidelity; `overview`: every element whose area exceeds a threshold, i.e. the coarse bulk, marked as such) and the meta and the figure caption say which elements are omitted. Nothing is resampled, smoothed or decimated: every kept element is a mesh element.

**Decision: the four uncached start meshes.** Experiment M0 first: regenerate each start mesh in its tree's recorded image (stable), with the committed cell and `selected.json` (`meshcut regenerate`, which runs the documented `moscap2d.build_device(..., mesh_file=...)` path in the sandbox and deletes the device), and compare its sha256 to the committed `mesh_sha256`. This is **not** mesh-only: `build_device` meshes the cross-section **and solves it at equilibrium** (its docstring: "Mesh and solve (at equilibrium) the cross-section"), so each regeneration costs meshing, device load and one equilibrium drift-diffusion solve on 205 k–503 k nodes, without the bias sweep. The regenerated mesh is written to `results/tcad/moscap2d/<device>/<params>/<gid>/mesh.msh` (git-ignored, beside the job's committed `cv.meta.json`), which is where `tools/output-cache push` scans for it. An implementing subagent never pushes to the cache.
2. **No match** (the expected case per the spec): no artefact is cut from that mesh, and the 2D job **is rerun**, as spec §10.1 requires ("the 2D job is rerun, so that the results and the artefact come from one mesh"). **Decision: regeneration policy.** A render is stale when any input file named in its manifest, its per-render generator hash or the render image pin changed. A stale render must be regenerated in the same PR (spec §10.1); the test makes that unavoidable. A change to a source tree's `provenance.json` alone (a restamp) never stales a render. When an upstream data tree is regenerated with identical bytes (for example Task B0's or Task F's restamps in the Charon plan), nothing goes stale. When it changes bytes (#35's calibrated reruns, the dev-image 2D reruns, a recalibration), the PR that commits the new data also reruns the affected renders: about 1–3 h of render time per device, scheduled one job at a time. To keep that bearable, a task that will change render inputs says so in its plan entry, and the renders are rerun once at the end of that PR, not per commit.

## Risks, each with the experiment that settles it

- **Blender determinism across hosts.** Cycles CPU with a fixed seed, fixed samples, no adaptive sampling and no time limit should be repeatable on one host; across CPUs, SIMD kernel selection and OIDN may change pixels. *Settled by* D1 (same host: twice, thread counts, OIDN on/off) and D3 (a GitHub runner). *Mitigation:* none needed for correctness: renders are outside bit-identity by spec; the manifest and the scene are what is checked. If D1 shows run-to-run variation on one host, the cause is recorded and the setting that causes it (OIDN, thread count) is fixed or dropped.
- **Headless GPU absence.** No GPU in the sandbox; EEVEE needs a GPU or software GL. *Settled by* the decision (Cycles CPU only) and `test_cycles_cpu_only`. EEVEE is never assumed; if a later render needs EEVEE-only effects, an experiment with Blender's headless EGL backend over Mesa llvmpipe is run first and recorded.
- **Image size.** About +1.1–1.3 GB over the shared base. *Settled by* I1 (measured, on the image page). *Mitigation:* none needed for the runner (the base is cached); deleting parts of the official tree is refused, because the image must hold an unmodified release.
- **GPL.** Blender binaries are GPL-3.0-or-later; publishing the image distributes them; bpy scripts are treated as part of the program. *Settled by* the decisions: unmodified official binary, source tarball mirrored and named in the image label and `SOURCES.json`, GPL headers on `render/blender/*.py`, the AST boundary, the README and image page notice. Renders are ours (licence page). The bundled libraries' sources (Python, FFmpeg/libvpx, OIDN and others) are not in Blender's source tarball; R2a Step 2b mirrors them or documents the GPLv3 §6(d) reliance per library. Reviewed in R2a and R2b.
- **Render time.** Estimated 10–40 s per 1080p frame for these scenes on 8 CPUs; R1 has 201 distinct frames per device. *Settled by* T1 (style card) and the draft renders. *Mitigation:* hold frames are copies, not renders; samples tuned down with OIDN on (D1 decides); draft at 640×360 for review; never a cheaper data set.
- **PNG size at 1080p.** A noisy Cycles PNG can exceed 2 MB. *Settled by* T1 and the first real still (R3-4). *Mitigation:* OIDN denoising, flat backgrounds, PNG compression 100, 8-bit RGB without alpha; if still over, the style's sample count and background are changed, not the budget.
- **WebM size and length.** 6 MB at 20 s needs about 2.4 Mbit/s VP9, ample for these scenes. *Settled by* the R3-1 encode; the size test enforces it.
- **2 MB artefact budget versus 205 k–503 k-node meshes.** Nodes concentrate along the oxide interface, so even a gate window holds a large share. *Settled by* M1 (window grid on the one mesh on disk, extrapolated to the 503 k cells). *Mitigation:* the two-window rule for the L = 2 µm cells (edge at full fidelity, overview of the coarse bulk elements, stated); never decimation or resampling.
- **The four uncached start meshes.** Not on any disk, not in the cache; regeneration may not reproduce the committed sha (stable image, older job format). *Settled by* M0 (four regenerations, each a mesh plus one equilibrium solve, one at a time, 1–4 h). *Mitigation:* no artefact is cut from an untied mesh. Each start job whose mesh fails M0 is rerun (spec §10.1) within #35's dev-image 2D reruns, one 16 GiB job at a time. Meanwhile the artefacts come from #35's calibrated trees, whose meshes are on disk and are pushed to the cache by the robot.
- **The profile hook holds an off-centre bias.** Settled by the code (`cv.py` lines 892–906): the device holds the converged Poisson–Boltzmann state at `vg − dv_fb_v + dv_qs`. *Mitigation:* `vg_held` is recorded and used, and `test_vg_held_matches_device` fails if a plugin change reorders the solves.
- **Profile file size.** ≈ 136 k rows per job. *Settled by* P2. *Mitigation:* n and p are never written, since they are exact Boltzmann functions of ψ derived in the manifest; if the file is still too large, bias stride 2.
- **Calibration replay not byte-identical.** If the recording wrapper changes the optimiser's path (it must not: it only forwards), or the result is host-dependent. *Settled by* the identity proof before writing. *Mitigation:* none needed if green; if red, the cause is a determinism bug in the calibration and is a Phase 2 finding, filed as an issue.
- **Mesh-convergence levels have no committed sha.** A node-count tie would not meet §10.1, so R3-5 waits. *Settled by* #35's dev-image meshconv rerun recording `mesh_sha256` per level (a one-line change in `meshconv`, made as part of that rerun, whose closure change is restamped there); level 1 may be tied earlier through the Lmin job's sha if M0 reproduces it.
- **Render churn when data changes.** Each byte-changing upstream rerun stales renders (1–3 h per device). *Mitigation:* per-render generator hashes; restamps never stale; reruns batched at the end of the data PR.
- **Charon B0 slips.** R0, R1b, R1c and R2b wait (no second registry change). R1a, R2a and the draft style work proceed; if B0 is blocked for more than a week, the plan is revisited with the owner rather than worked around.
